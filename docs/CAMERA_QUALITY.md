# 카메라 화질 · AI 배경제거 (Camera Quality & Background Removal)

촬영 화질과 AI 배경제거(세그멘테이션)의 **현재 구조 · 한계 · 개선 방안 · 사이드 이펙트**를 한곳에 정리한다.
"손가락이 잘린다", "경계가 지저분하다" 같은 이슈를 만졌을 때 여기부터 본다.

---

## 1. 현재 파이프라인

### 1-1. 사용 모델

- **MediaPipe `ImageSegmenter`** — 모델 `selfie_multiclass_256x256.tflite`
- 입력을 **항상 256×256으로 축소**해 추론한다. 모델 자체의 고정 입력 크기라 **바깥에서 해상도를 올려도 내부에서 256으로 다시 줄인다.**
- `outputConfidenceMasks: true` — 클래스별 confidence 마스크를 받는다.
- 멀티클래스 모델이지만 **`masks[0]`(배경)만** 사용하고, 전경 = `1 - 배경`으로 계산한다(어두운 옷·머리카락 보존 목적).

### 1-2. 두 개의 렌더 경로 (동일 수식)

| 경로 | 구현 | 언제 |
|------|------|------|
| 송출(서브 모니터) | `CameraStreamer` | 카메라 단계가 **아닌** 화면(배경 선택 등) |
| 촬영 화면·촬영본 | `useCameraCapture` (+ 워커) | 카메라 단계 + 실제 셔터 |
| 관리자 미리보기 | `usePreviewCamera` | `/admin/preview` 튜닝 다이얼로그 |

- 세 경로가 **같은 마스크 코드**(`src/lib/segmentMask.ts`)를 쓴다. 즉 설정값 조정이 미리보기·송출·촬영에 일관되게 반영된다.
- 추론은 무거우므로 매 프레임이 아니라 **스로틀링**해서 돈다. 사이 프레임은 마지막으로 구워 둔 마스크
  캔버스를 GPU 합성(`destination-in`)으로 재사용한다 — 프레임마다 픽셀 루프를 다시 돌지 않는다.

### 1-3. 촬영본 처리 (중요)

- 촬영본은 **별도 추론을 다시 돌리지 않는다.** 프리뷰에서 만든 **저해상도(256) 마스크를 그대로 확대 적용**한다.
- 즉 **프리뷰에서 잘린 손가락은 인화본에도 똑같이 잘린다.** 촬영본만 따로 좋게 만들려면 촬영 시점 전용 처리(→ 3-3)가 필요하다.
- 인화 해상도 상한 `CAPTURE_MAX_W = 1800`(10×15cm 300DPI 기준). 그 이상은 인쇄상 무의미.

### 1-4. 마스크 후처리 (ROI 크롭 · 공간 블러)

경계 계단(에일리어싱) 대책으로 두 단계가 더 있다. 둘 다 `src/lib/segmentMask.ts`에 있고,
**촬영(`useCameraCapture`) · 송출(`CameraStreamer`) · 관리자 미리보기(`usePreviewCamera`)
세 경로가 모두 같은 코드를 공유한다** (촬영 경로는 워커/메인 스레드 폴백도 동일).
미리보기가 실제 화면과 다르게 보이면 슬라이더를 아무리 맞춰도 소용이 없으므로, 세 경로를
갈라두지 말 것.

- **ROI 크롭 추론** (`nextRoi`) — 직전 마스크의 전경 bbox에 여유를 붙인 사각형만 잘라 다음 추론에
  넣는다. 모델 입력이 256×256 고정이라 프레임 전체를 넣으면 경계 해상도가 `프레임 폭 / 256`으로
  묶이는데, 크롭하면 같은 격자가 더 좁은 면적을 덮어 **계단 폭이 실제로 줄어든다.**
  - 정사각·프레임비율로 맞추지 **않는다.** 부스에서 인물은 보통 세로를 거의 채우므로 비율을 맞추면
    어떤 크롭도 프레임만 해져 이득이 사라진다. 변마다 여유를 붙이고 프레임으로 자른다 —
    위아래는 이미 화면이 인물을 자르므로 끝까지 가고, **좌우만 좁아진다.** 실루엣의 주요 경계가
    세로 방향이라 가로 해상도가 곧 계단 폭이다.
  - 어느 축도 의미 있게 줄지 않으면(`ROI_WORTH_RATIO`) `null` → 프레임 전체로 추론(기존 동작).
    관리자 설정 `CAPTURE_ROI`를 끄면 항상 `null`이다.
  - 인물이 크롭의 **안쪽** 경계에 닿으면 여유를 두 배로 잡고 EMA 없이 즉시 넓힌다. 프레임 끝에
    맞닿은 변은 원래 화면이 자르는 자리라 판단에서 뺀다.
- **공간 블러** (`bakeBlurredMask`) — 구워진 마스크에 `ctx.filter = blur()`를 건다. 반경은 256 격자
  텍셀 크기에 비례하므로 ROI로 좁게 볼수록 자동으로 약해진다.
  - 블러는 캔버스 바깥을 투명으로 보기 때문에, 어깨처럼 **화면 끝에 닿은 부위**가 그대로 블러되면
    프레임 가장자리에 반투명 띠가 생긴다. 패딩 캔버스에 가장자리 1px을 복제(edge clamp)한 뒤
    블러하고 되잘라 이를 막는다.
- **경계 두께 · 시간축 평활** (`createMaskBaker`) — 블러 뒤 알파에 한 번의 픽셀 패스로 적용한다.
  - 두께는 `a^g` **감마 곡선**이다. 알파를 그냥 더하고 빼면(평행이동) 실루엣 **내부**(알파 1.0)까지
    같이 내려가 인물 전체가 반투명해진다. 감마는 0과 1을 고정점으로 두고 전환대만 움직인다.
    곡선은 256칸 LUT로 미리 구워 둔다.
  - 평활은 이전 마스크와의 선형 보간이다. 되먹이는 값은 **두께 보정 전** 알파다 — 보정 후를
    되먹이면 프레임마다 두께가 누적돼 실루엣이 계속 부풀거나 사라진다.
  - 픽셀 패스는 추론마다 한 번만 돈다(매 프레임이 아니라). 둘 다 기본값이면 패스 자체를 건너뛴다.
- 마스크 캔버스(`maskCanvasRef`)는 ROI 유무와 무관하게 **항상 프레임 전체**를 덮는다. 소비하는
  쪽(프리뷰 `destination-in`, `captureHiRes`)은 크롭을 몰라도 된다.
- 세기는 전부 관리자 촬영 설정에서 온다(6장 표). 스크래치 캔버스와 평활 상태는 `createMaskBaker()`가
  들고 있어 합성 경로끼리 섞이지 않는다 — 경로마다 하나씩 만들어 쓴다.

> 세 경로의 남은 차이는 **처리 해상도와 카메라 요청 비율뿐**이다 — 미리보기는 1280×720(16:9)에
> `PROCESS_SCALE` 0.5 고정, 서비스는 4:3에 4K에서 0.25로 낮춘다. 블러 반경이 처리 해상도에
> 비례하므로 보이는 결과의 성격은 같지만, 화각 자체는 미리보기와 촬영이 다르다.

### 1-5. 마스크 합성 수식

```
alpha = clamp01( (fgConf - THRESH) / FEATHER )     // fgConf = 1 - 배경확신도
```

기본값(THRESH=0.15, FEATHER=0.35) 기준:

- `fgConf ≤ 0.15` → 완전 제거(투명)
- `fgConf ≥ 0.50` → 완전 불투명(사람)
- 그 사이 → 반투명 전환대(soft edge)

- `THRESH` = 알파가 0에서 올라가기 시작하는 컷오프 지점
- `THRESH + FEATHER` = 알파가 1(완전 불투명)에 도달하는 지점

## 2. 왜 손가락이 잘리나 (근본 원인)

1. **256×256 저해상도 모델** — 손가락처럼 얇은 부위는 256px에서 몇 픽셀밖에 안 돼 모델이 통째로 놓치거나 뭉갠다. **가장 큰 원인.**
2. **촬영본이 프리뷰 마스크 재사용** — 프리뷰의 손끝 잘림이 인화본에 그대로 박힌다(1-3).
3. **임계값 컷오프** — 손끝·외곽은 모델 confidence가 원래 가장 낮은 곳이라, `THRESH` 아래로 떨어지면 우선적으로 잘린다.
4. **국소 조정 불가** — 임계값은 마스크 전체에 일괄 적용된다. 손끝을 살리려면 실루엣 전체가
   느슨해지는 걸 감수해야 했다. → **`CAPTURE_HAND_RESCUE`로 해소됨**(1-4): 제스처 인식기가
   찾아낸 손 주변에서만 컷오프를 낮춘다.

> ⚠️ **막다른 길:** 프리뷰 캔버스 해상도를 올려도 개선되지 않는다. 모델이 내부에서 256으로 줄이기 때문(1-1).

## 3. 개선 방안

| 개선 | 상태 | 라이브 | 인화본 | 비용 |
|------|:---:|:---:|:---:|:---:|
| 3-1. 설정값 튜닝 | ✅ 가능 | ✅ | ⚠️ (3-3 없을 때만) | 없음(숫자만) |
| 3-2. 마스크 후처리 | 🟡 일부 도입 | ✅ | ⚠️ (3-3 없을 때만) | 중간 |
| 3-3. 촬영 전용 고품질 모델 | ❌ 미도입 | ❌ | ✅✅ | 큼 |
| 3-4. 라이브 모델 교체 | 🚫 비권장 | — | — | — |

- **3-3이 사실상 본체(약 80% 가치)**, 3-1·3-2는 프리뷰 폴리시. 3-3을 도입하면 인화본은 더 이상
  프리뷰 마스크를 쓰지 않으므로 3-1·3-2는 **프리뷰 화면 정확도 전용**으로 역할이 좁아진다.

### 3-1. 설정값 튜닝 (코드 X, 관리자에서 즉시)

경계 관련 8종을 `/admin/capture-setting`에서 조정하고 미리보기로 바로 확인한다(1-4, `SPEC.md` §12).
→ **부작용은 4장 참조.**

### 3-2. 마스크 후처리 — 🟡 일부 도입

**도입됨**(1-4): 공간 블러 · ROI 크롭 추론 · 경계 두께(감마) · 시간축 평활. 세 합성 경로가 공유한다.

**남음 — guided filter**: 마스크를 실제 RGB 윤곽에 스냅시킨다. 지금 도입된 것들은 모두 마스크만
보고 다루는 후처리라 "모델이 놓친 손가락"을 되살리진 못한다. guided filter는 원본 영상의 엣지를
참조하므로 윤곽이 실제 경계를 따라간다 — 질적으로 다른 개선이고, 남은 항목 중 유일하게 그렇다.
실시간 비용은 중간(마스크 해상도에서 돌려 스로틀 budget 안에 유지). WebGL 셰이더가 현실적.

### 3-3. 촬영 순간 전용 고품질 모델 (권장 · 미도입)

라이브 프리뷰는 지금의 빠른 256 모델 유지, **셔터가 눌린 그 한 프레임만** 고해상도 매팅 모델
(예: RobustVideoMatting / MODNet / RMBG 계열)로 다시 세그먼트.
→ 한 컷 지연은 촬영 시점에 허용됨. 손님이 가져가는 **인화본 품질이 직접 좋아진다.**

> `captureHiRes()`가 촬영 순간 원본 해상도로 합성하긴 하지만 **프리뷰 마스크를 확대 재사용**할
> 뿐이라(1-3), 모델 품질 자체는 그대로다.

**도입 시 검토할 것:**
- 번들·로딩: 모델(수~수십 MB) + 런타임(ONNX/WASM) → 키오스크 초기 로딩·오프라인 캐싱
- 촬영 지연: 셔터당 무거운 추론 1회 → 카운트다운 흐름에 배치, 프리워밍/로딩 상태 처리
- 코드 경로 2개(라이브/촬영) → 폴백(촬영 모델 실패 시 기존 프리뷰 마스크) 필요
- 설정 UX: 도입 후 관리자 슬라이더가 **프리뷰만** 바꾸게 됨 → 촬영 모델에도 연동할지 정책 결정

### 3-4. 비권장 — 라이브 모델 교체

MediaPipe에 256보다 뚜렷이 나은 공식 tflite가 없어, 실시간 고해상도는 서드파티 모델 필요 →
키오스크 FPS 위험. **256 격자를 512로 늘리는 건 불가능하다** — 입력 텐서 크기가 `.tflite`에
고정돼 있고, 모델 자체도 256에서 학습됐다. 대안은 (a) ROI 크롭으로 격자가 덮는 면적 줄이기
(도입됨), (b) 촬영 순간 타일 분할 추론(2×1 = 프레임 기준 512 격자, 추론 2배), (c) 3-3.

## 4. 설정값 튜닝 사이드 이펙트 (3-1 상세)

손가락을 살리려면 `THRESH`를 낮추거나 `FEATHER`를 넓혀야 하며, 각각 부작용이 다르다.

### THRESH를 낮추면 (예: 15 → 5%)

- **배경 헤일로/프린지** — confidence 낮은 배경 픽셀(0.05~0.15)이 반투명으로 남아, 사람 주변에 원래 촬영 배경(실제 방)이 얇게 비쳐 합성 배경 위에서 지저분한 테두리로 보인다.
- **주변 물체 유입** — 인물에 붙은 저확신 배경(팔 옆 벽 등)이 딸려 들어온다.

### FEATHER를 넓히면

- **윤곽 고스팅** — 실루엣 경계 전체가 더 반투명해져 배경이 비치는 반투명 테두리. 심하면 몸 외곽까지 흐릿.
- 반대로 너무 낮춰도 **계단은 FEATHER로 못 고친다.** FEATHER는 confidence라는 **값 축**만 완만하게
  만들 뿐 **공간 축**은 건드리지 않는다. 계단은 마스크의 기하학적 형태가 256 격자에 양자화돼서 생기는
  것이라, 공간 블러(1-4)나 ROI 크롭(1-4)으로 다뤄야 한다. FEATHER를 넓히면 계단이 덜 보이는 대신
  고스팅만 늘어난다.

### 공통

- **프레임 간 깜빡임(flicker)** — 손끝·경계는 모델 confidence가 원래 불안정한 곳. 임계값을 낮출수록 그 불안정 픽셀이 드러나 가장자리가 프레임마다 떨린다. 라이브에서 특히 눈에 띄고, 그 프레임이 촬영되면 인화본에도 박힌다.
- **국소 조정 불가** — 임계값은 마스크 전체 일괄 적용. 손끝을 살리려면 실루엣 전체가 느슨해지는 걸 감수해야 한다(2장-4).

### 안심해도 되는 부분

- **크로마키·off 모드 무관** — THRESH/FEATHER는 mediapipe 모드 전용. 크로마키는 별도 파라미터(similarity/smoothness).
- **성능 영향 0** — 같은 픽셀 루프에 숫자만 바뀜. FPS·로딩 변화 없음.
- **완전 가역** — 숫자 하나라 언제든 원복. 나눗셈 0 방지로 FEATHER는 최소 1%로 clamp.
- **적용 범위** — 기기 설정이라 특정 기기만 바꾸면 그 기기만 영향.

### 권장 접근

작게 단계적으로. 예: **THRESH 15→10, FEATHER 35→40**로 먼저 보고, 헤일로가 거슬리면 되돌린다.

### 설정 값 의미

**설정 키·기본값의 정본은 `SPEC.md` §12 표**다(여기서 되풀이하면 기본값이 어긋난다).
코드 변수명은 `CAPTURE_*` → `DeviceConfig.segment*`로 1:1 대응한다(`useDeviceSetup.ts`).

튜닝할 때 헷갈리는 두 쌍만 여기 적는다.

**`CAPTURE_THRESHOLD` vs `CAPTURE_EDGE_SHIFT`** — 둘 다 경계를 안팎으로 옮기지만 기준이 다르다.
THRESHOLD는 **모델 확신도**를 자르는 지점이라 확신이 낮은 곳(손끝·머리카락)부터 우선 사라진다.
EDGE_SHIFT는 블러 뒤 알파에 감마 곡선을 걸어 **실제 거리**로 경계를 민다 — 실루엣 전체에 고르게
작용하므로 "폭이 일정한 헤일로"를 걷어낼 때 이쪽이 맞다. 손끝을 살리려면 THRESHOLD를 낮추고,
그때 생긴 테두리를 EDGE_SHIFT(−)로 깎는 조합이 궁합이 좋다.

**`CAPTURE_SMOOTHNESS` vs `CAPTURE_MASK_BLUR`** — 부드러움은 confidence라는 **값 축**, 블러는
**공간 축**이다. 경계 계단은 공간 문제라 부드러움을 아무리 넓혀도 안 없어지고 고스팅만 는다(4장).

### 손가락이 사라질 때 — 순서대로

실측 사례: 어느 지점의 `CAPTURE_THRESHOLD`가 **60**으로 올라가 있어 V포즈의 검지가 통째로
사라졌다. 확신도 60% 미만은 전부 잘리는 설정이라, 확신도가 원래 가장 낮은 손끝이 먼저 사라진다.

1. **`CAPTURE_THRESHOLD`를 10~15로.** 대부분 여기서 해결된다. 20을 넘기면 손끝이 위험하다.
2. 그래서 배경 헤일로가 생기면 **`CAPTURE_EDGE_SHIFT`를 −20~−40**으로. 확신도가 아니라 거리
   기준이라 손끝을 다시 먹지 않는다. THRESHOLD를 올려 헤일로를 잡던 예전 방식을 대체한다.
3. 여전히 손가락만 약하면 **`CAPTURE_HAND_RESCUE` 40~70**. 손 주변만 국소로 컷오프를 낮춘다.
4. **해상도는 대개 원인이 아니다.** ROI 크롭이 걸리면 손가락 폭이 256 격자에서 보통 10텍셀을
   넘는다 — 모델이 형태를 잡기엔 충분하다. 계단이 아니라 *사라짐*이면 임계값을 먼저 의심할 것.
